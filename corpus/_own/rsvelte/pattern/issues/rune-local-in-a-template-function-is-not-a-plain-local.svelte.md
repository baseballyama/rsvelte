# `rune-local-in-a-template-function-is-not-a-plain-local.svelte`

**Issue:** shadow probe

The predicate `prop-shadowed-by-local-in-template-handler.svelte` introduced, `reference_is_plain_local`, over-fired on the shape #3233 fixed: phase 2 records a **second, `Normal`** entry for a rune declared inside a template expression's function body, so `let counter = $state(1); counter = 2` in a handler answered "plain local", `try_transform_assignment` bailed, and the fallback emitted `$.set(counter, 2, true)` where official emits `$.set(counter, 2)`. The scope chain separates the two: a component binding is declared at instance depth, a local signal one function deeper — so the veto is `State`/`RawState`/`Derived` at `function_depth >= 2`, and restricting it to those three kinds is load-bearing, because an each item is also a nested non-`Normal` binding and vetoing on that alone put the `$$index` parameter back. The second handler writes a plain local and then a prop member, as the positive control. Ablated, the repro reports the wrong third argument on `client` and `client-dev`; the shape moves no corpus output either way. The runes are read from a **closure** on purpose: upstream's `state_referenced_locally` walk stops at a function boundary, and a bare `use(counter + raw)` made this file assert a warning class the template path does not reach — phase 2's Identifier visitor never enters a template expression's function body, so official's two warnings for that read had no counterpart and the file landed as four NEW warning-ratchet entries. The lowering this file exists for is the WRITE, and the closure keeps it: ablated it still reports 2 of 4.
