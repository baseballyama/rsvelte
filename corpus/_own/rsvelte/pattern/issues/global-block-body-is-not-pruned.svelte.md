# `global-block-body-is-not-pruned.svelte`

**Issue:** [#4089](https://github.com/baseballyama/rsvelte/issues/4089)

Upstream’s prune visits a global block’s **prelude** and not its body (`2-analyze/css/css-prune.js:133`), so a `.p` prefix still scopes what it matches and nothing written inside the block scopes anything. rsvelte read that decision off `metadata.is_global_block` — a key **read once and written nowhere**, so the short-circuit was unreachable and the body was walked like any other nested rule. A `&` in the subject then reached `nesting_matches_anything`, which matches every element, so `.p :global { &.a { … } }` scoped `path`, `i` and `u` beside the `svg` the prefix matched. The children are crossed in one file because only a `&`-subject cell moves: `.a`, `& .b` and `:global(.c)` inside the same block are the in-block controls that were already correct, and the trailing `.p { & .a { … } }` is the out-of-block control that must go on being walked. The predicate had to be widened at the same time, and the `:global.q` block is the half that measures it: `is_bare_global_relative` requires the relative selector to be **exactly** `:global`, while upstream opens a block on any relative selector whose *first* simple selector is a bare `:global`. Those cells are nested because a `:global.x` is only legal where it is not the first relative selector of a root rule, and they move with no `&` anywhere — `.b` inside them was scoped too — so the defect is not about `&` even though the reported cell was. Ablating the short-circuit and ablating the widening redden different tests.
