# `a-var-is-function-scoped-not-block-scoped.svelte`

**Issue:** shadow probe

A `var` outlives the block it is written in, so `{ var v = 2; } typeof v` resolves to the local — and all **three** phase-3 shadow registrars scoped it to the block: the server's `read_wrap.rs` pushed a frame per block whose doc claimed collecting `var` at every block boundary was "conservatively correct" (it is not, because the frame is popped), the client's instance-script pass declared into whichever scope the walk was in, and the template walker's `register_block_local_vars` only ever read the statement list it was handed. Every `var` site except a function's own top level was wrong on client AND server: a block, an `if` consequent, a `for` init, a `for…of` head, a `try` block, a `case` arm, a `while` body and a doubly nested block — 42 of 56 comparisons on the grid, against the 6 the original probe showed. `nested()` is the positive control: a `var` inside a nested function must NOT leak out, which is what stops the fix from being "collect every var anywhere". The server and instance-script ports walk the same oxc AST and now share one `shared::hoisted_vars` walk rather than a copy each. Ablated per port: 18 server, 18 instance-script, 8 template, 44 with all three removed. 0 of 34,728 corpus entries move on client, client-dev or server. What the grid still leaves open is `for (var v = 0; v < 1; v++)` in a template handler, where the READ is now right and the UPDATE still lowers to `$.update(v)`: that decision belongs to a fourth predicate, `reference_is_plain_local`, whose answer comes from phase 2.
