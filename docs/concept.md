## 2. レビューの方針

各主張について **(a) 最も強い反論 → (b) 判定 → (c) 確定した形** の順に書く。判定は次の 3 種類。

- **維持**: 反論に耐えた
- **修正**: 狙いは正しいが、書かれた形のままでは壊れる
- **棄却**: 狙いを別の手段で達成する

## 3. 敵対的レビュー

### C1 ゼロからの書き直し — 判定: 修正（書き直す。ただし「何を断つか」を先に列挙する）

**反論**

1. **セカンドシステム症候群。** 書き直しが失敗する典型は、「前回できなかったことを全部やる」設計が最初の動く縦串より先に来ること。C3 と C4 は、まさにその形をしている。
2. **負債を名指さない書き直しは、同じ負債を作り直す。** 旧実装の負債は具体的に言える。
   - `serde_json::Value` の AST とその JSON 実体化（アロケーションの大半を占める）
   - instance script の文境界を文字走査で決めていること（unparseable output の全件の原因）
   - 1 つの上流関数に 2 つ以上のポートがあること（client/server、text/AST、CLI/LSP）。しかも port 同士を比べるゲートが無い
   - 変換後テキストを再パースする text pipeline
   - comment の位置を `loc_base` のような 1 つの u32 に二つの意味で持たせたこと
3. **出力を上流と一致させる限り、アーキテクチャは上流の出力形に拘束される。** drop-in を掲げたまま「JS 由来の構造から自由になる」ことはできない。自由になれるのは内部表現と実行順序であって、出力ではない。
4. **旧実装は捨てると高くつく資産でもある。** 数万ファイルで上流と一致するようになった Rust 実装は、新実装にとって最速の差分オラクルであり、性能ベースラインでもある。

**確定**

- 書き直しの目的を「上の 5 つの負債クラスが**構造的に起こりえない**設計」と定義する。設計レビューでは、各クラスについて「新設計ではなぜ起きないか」を 1 行で言えることを要件にする（§4-P1〜P7 が答え）。
- 出力の正しさは引き続き上流オラクルに対して測る（§8-Q2）。
- 旧 rsvelte（`main`）は差分オラクル・性能ベースラインとして固定版を維持する。新旧でバイト一致しない差分は「新実装の欠陥」「旧実装の欠陥」「意図的な差」の 3 バケツに分類する。

### C2 Runes ファイルのハードコピー fixture — 判定: 修正（量は十分。ライセンスとモードの定義を足す）

**反論**

1. **ライセンス。** ハードコピーは再配布にあたる。§0 のとおり 23 ソース（Runes 明示 2,619 件）は GPL / AGPL / ライセンス無しなどに属する。AGPL・GPL のファイルをリポジトリにコミットすると、そのファイルには当然そのライセンスが付いたままになる。ライセンス無しのファイルには、そもそも再配布権が無い。submodule 方式はリンクを張るだけなので、この問題を踏まずに済んでいた。
2. **「Runes」の定義が 3 通りあり、どれを採るかで出力が変わる。** 上流はファイルごとにモードを推論する。中立ファイル（9,444 件）は、既定の config では **legacy モードで compile される**。同じ入力でも、`runes: true` の config 下では出力が異なる。つまり「Runes ファイルだけ」と言うとき、ファイルの性質を言っているのか (入力, config) の組を言っているのかを決めないと、期待出力が一意に定まらない。
3. **ファイル単体は文脈を持たない。** compile・fmt・構文 lint は単体で閉じる。しかし型検査・型付き lint・`svelte.config` の preprocess（`lang="scss"`、pug など）はプロジェクト文脈を要する。単体ファイルの fixture では C9 を検証できない。
4. **実コーパスは相互作用のバグを持たない。** 旧プロジェクトの経験では、相互作用バグは 30k 実ファイル中に 0 回しか現れなかった。実コーパスは床であって天井ではない。
5. **`.svelte.ts` の 715 件は、TS を剥がす段なしには compile の入力にならない。** 上流では、この段を Vite が担っている。

**確定**

- **fixture の単位は `(入力, オプション, モード)` の組にする。** マニフェストには少なくとも、出所（repo URL、commit sha、元パス）、ライセンス、sha256、オラクルが推論したモード、期待出力を生成したオラクルの版を記録する。
- 取り込むのは「オラクルのモードが runes のもの」（Runes 明示 12,330 件と、Runes モジュール）。中立ファイルは `runes: true` を明示したオプションの組としてのみ取り込み、既定モードでの期待出力とは混ぜない。
- **ライセンスの扱い** はユーザーの決定事項（§8-Q1）。推奨は、permissive のみコミットし、それ以外はローカル専用コーパスにすること（取り込みスクリプトは両方を扱える形にする）。
- プロジェクト文脈が要るタスク（型検査・型付き lint・preprocess）用に、ファイル fixture とは別に **project fixture**（tsconfig と依存の宣言を含むスナップショット）を持つ。これもライセンスで同じ選別をかける。
- 実コーパスとは別に、**生成コーパス**（軸の直積から作る matrix と mutation）を最初から一級の fixture として持つ。
- 取り込みは再実行できるスクリプトにする。固定したソース commit から、何度実行しても同じバイト列を出すこと。

### C3 何でも入る抽象パイプライン — 判定: 修正（「万能 AST」は棄却し、「多言語文書＋lowering グラフ＋クエリ」にする）

**反論**

1. **万能 AST は最小公倍数か、JS の形かのどちらかに落ちる。** JS と CSS と Markdown に共通するノード種はほぼ無い。`dyn Node` で抽象化すれば、型安全と、C6 が求めるメモリ配置の両方を失う。
2. **rustc の多段 IR は 1 言語の話である。** 多言語コンパイラ（GCC、LLVM）が IR を共有するのは下流の低レベル段であって、AST ではない。ここで AST 段の共有を目指すのは、先例のない方向である。
3. **本当に共有できるのは木ではなく、木の周りである。**
   - ソース管理（ファイル DB、行インデックス、UTF-8/16 変換）
   - span と source map の**合成**
   - 診断、インターン、アリーナ、キャッシュ、スケジューラ、設定、計測
   - そして最重要の「**言語 A の中に言語 B の領域がある**」という埋め込みモデル（Svelte の script/style/式、Vue SFC、HTML の script/style、Markdown のコードフェンス、Pug のテンプレート）
4. **「最適化フェーズ」は射程を膨らませる。** バンドル・minify は Rolldown/oxc の仕事であり、ここで再実装すると競合相手が一つ増えるだけになる。さらに Svelte の出力は `svelte/internal` という**非公開 API** を呼ぶ。上流と違うコードを出す最適化は、ユーザーのプロジェクトに入っている runtime の版との互換を自分で背負うことになる。

**確定**

- 共有するのは次の 4 つ。
  - **カーネル**: SourceDb / Span / SourceMap 合成 / Diagnostics / Interner / Arena / Query キャッシュ / Scheduler / Configuration / Metrics
  - **埋め込みモデル**: 文書は、言語タグ付きの領域の木として表す。Kernel boundary: a document holds its path and text, without a language ID. Plugins decide which documents their tasks and facet providers handle. Embedded language tags belong to the plugin's tree, not the kernel's document.
  - **lowering グラフ**: 言語プラグインは「X → Y へ下げられる」を宣言する（Pug→HTML テンプレート、Sass→CSS、TS→JS、Markdown→Svelte、Svelte→JS+CSS、Svelte→TS 射影）。source map は辺ごとに合成する
  - **フェーズ契約**（§4 の段）
- **木そのものは言語ごとに専用の型**にする。JS/TS の木も自前で持ち、パーサはその木を組み立てる差し替え可能な部品にする（§3-C10）。
- 「最適化」の射程は、**上流 Svelte が出力で既に行っていること**（静的ホイスト、テンプレート clone など）の範囲に限る。上流の出力と意味的に異なるコードは、runtime テスト付きのオプトインとしてのみ許す（§8-Q2）。
- 抽象は 2 言語目で抽出する（三度目の法則の緩和版）。最初の縦串は Svelte だけで作るが、カーネルの API は「Markdown 内の Svelte」（mdsvex 形）を2 例目として想定し、埋め込みが入れ子になっても成立することを確認する。

### C4 対象言語 — 判定: 修正（段階を切る）

**反論**: 10 言語を同時に一級で扱うのは、C1 の反論 1 そのもの。しかも Sass には dart-sass と完全互換な Rust 実装が無い（旧実装の `grass` は ratchet 付きで乖離を管理していた）。Pug はニッチ。Vue は、Vue 自身のコンパイラという強力な上流と競合する。

**確定**

| 段 | 言語 | 位置づけ |
|---|---|---|
| Tier 1 | Svelte（Runes）、JS、TS、CSS | 縦串。すべてのタスク（compile / lint / fmt / 型検査）を通す |
| Tier 2 | HTML、Markdown（mdsvex 形）、SCSS | 埋め込み・lowering の汎用性を検証する 2 例目・3 例目 |
| Tier 3 | Vue、TSX、Pug、Sass（indented）、その他 | プラグイン ABI の最初の外部利用者として作る。コア側の特例は作らない |

### C5 1 回のパースで全処理 — 判定: 修正（「parse once」ではなく「compute once」。ただし効果は計測してから主張する）

**反論**

1. **Amdahl。** 共有パースで節約できるのは、各タスクに占めるパースの割合までである。compile は変換・出力が支配的で、lint はルール実行が、fmt は印字が支配的な可能性が高い。パースの割合を測る前に「高速化できる」とは言えない。
2. **タスクごとに欲しい木が違う。** fmt はコメントとトリビアと元のトークン境界を要する（lossless）。compile は意味的 AST と scope を要する。lint はその両方を要する。1 つの木で済ませるには、その木を lossless にするか、AST ＋ トリビア/コメントの側表（oxc 方式）にする必要がある。
3. **変換は木を書き換える。** compile が共有の木を in-place に書き換えれば、同時に走る lint が壊れる。共有する木は不変でなければならない。
4. **`--fix` と fmt はソースを書き換える。** その時点で再パースが要る。「1 回」は修正モードでは嘘になる。
5. **タスクが本当に同時に走る場面は限られる。**
   - エディタ（LSP）: lint + fmt + 診断 + 型検査が同じ文書に対して走る → 同時
   - CI / pre-commit: `check + lint + fmt --check` → 同時
   - Vite: compile のみ（オーバーレイ用に lint が乗る程度）

   つまり共有の価値は LSP と CI にあり、Vite にはほぼ無い。

**確定**

- 中核は、**派生事実のデータベース**（surface tree、semantic、lowered IR、射影）にする。これで「1 回のパース」は「**同じ派生物は 1 回だけ計算する**」に一般化される。
  - 実装（`rsvelte_kernel::db`）は文書ごとの遅延キャッシュで、タスクは派生物を `ctx.get` で求め、初回だけ計算される。宣言と事前の計画は持たない。計画が要らないのは、依存を `get` の呼び出しがそのまま表しているからである。
  - 内容ハッシュをキーにして時間方向（LSP、デーモン、watch）に持ち越す部分は、まだ実装していない。
- 共有する木は**不変**にする。変換は新しい木（lowered IR）を作る。rustc の AST→HIR→MIR と同じ規律である。
- `--fix` は「修正 → 増分再パース → 収束するまで反復」を明示的なループとして持ち、反復回数を計測値として出す。
- **仮説 H5**: CI 形の `check+lint+fmt` 同時実行は、個別実行の合計より速い。これをパース割合の実測とともに縦串で検証する。反証されたら、共有の価値は LSP 側だけにあると書き直す。

### C6 マルチスレッド・メモリ配置・計測基盤 — 判定: 維持（ただし並列の単位を「ファイル」に固定する）

**反論**

1. **ファイル内並列はほぼ損になる。** 1 ファイルの処理は数十 µs〜数 ms で、スレッド間の受け渡しとキャッシュミスのほうが高くつく。
2. **外部の AST は、スレッド間で共有できる保証が無い。** たとえば `oxc_ast` 0.145 のノードは `scope_id: Cell<Option<ScopeId>>` を持ち（`src/syntax_tree/js.rs:68` ほか）、`unsafe impl Sync` も無い。したがって `&Program` は `Send` ではない。自前の AST を持つ（C10）ことでこの制約は消えるが、oxc をパーサとして使う場合は、変換が終わるまで oxc の木を作ったワーカーの外に出さない。
3. **Vite の中では並列度を呼び出し側が決める。** Vite はモジュールを要求順に 1 つずつ transform に渡すので、ライブラリ側でスレッドを増やしても並列度は上がらない（先読みコンパイルをしない限り）。
4. **CPU サイクルへの執着は、正しさより先に来ると害になる。** 旧実装の性能の教訓（serde_json の撤去など）は、どれも「正しく動く実装をプロファイルした結果」だった。

**確定**

- **並列の単位はファイル（文書）にする。** 1 ファイルに対するタスク群は、同じワーカーで順に実行する（データがキャッシュに乗ったまま）。ファイル間は work-stealing で並列にする。
- **意味情報は木の外の側表**（`NodeIdentifier` → 情報）に持たせ、自前の木は `Sync` に保つ。外部パーサの木は変換の間だけ存在させ、作ったワーカーの外に出さないことを型で強制する。
- メモリは、ファイル単位のアリーナ（処理が終われば一括解放）、u32 の span、インターンしたアトム、ホットなフィールドの SoA 化で組む。`serde_json::Value` は内部表現としては使用を禁止する（公開 JSON 出力は印字時に直接書く）。
- **計測基盤は 3 層で、最初のコミットから入れる。**

| 層 | 量 | 用途 |
|---|---|---|
| L0 決定的 | 命令数（Linux: `performance stat` / callgrind 系）、アロケーション回数・バイト数（カウンティングアロケータ）、ピーク RSS | CI のゲート（ノイズが無いので ratchet にできる） |
| L1 フェーズ | ファイル × フェーズごとの時間とアロケーション。feature で切ればコストゼロ | どこに効いたかの帰属 |
| L2 エンドツーエンド | コーパス全体の wall time、Vite の cold build、HMR の p50/p99 | 報告。A/B は時間内でペアにして ABBA で測り、アーム内のドリフトも併記する |

- 比較対象は最初から 3 本立てにする: **上流 JS ツール**、**旧 rsvelte**、**新実装**。ベンチマークの母集団は fixture そのもの（C2）。

### C7 Vite / Rolldown 接続とデーモン — 判定: 修正（1 プラグインは維持。CSS は Vite に返す。デーモンは既定にしない）

**反論**

1. **CSS は Vite のパイプラインを通さなければならない。** PostCSS、Tailwind、lightningcss、CSS modules はすべて Vite 側の CSS パイプラインに乗っている。一発処理の中で CSS を完結させると、それらを再実装するか壊すかのどちらかになる。
2. **Vite はすでに常駐プロセスである。** in-process の NAPI アドオンは、それ自体が温まった常駐状態を持つ。外部デーモンは、そこに IPC（ソースと出力のシリアライズ・コピー）を足すだけになる可能性が高い。
3. **デーモンには固有の運用コストがある。** 陳腐化した状態、プロジェクトごと・版ごとの多重起動、ソケットの権限、Windows の named pipe、メモリの増え続け、クラッシュ時の復旧。
4. **Rolldown に第三者のネイティブプラグインを差し込む安定した方法は、（調べた範囲では）無い。** Rolldown の組み込みネイティブプラグインは Rolldown のバイナリの一部である。第三者のプラグインは JS フック経由になり、NAPI を往復する。

**確定**

- Svelte 部分（compile、HMR 差分、Svelte 固有の resolve）は Vite プラグイン 1 つが一発で担う。**CSS は仮想モジュールとして Vite に返し**、Vite の CSS パイプラインに通す。
- JS フックの呼び出し回数を最小にするため、hook filter（id パターン）を使う。Svelte 以外のモジュールでは JS に入らない。
- **既定は in-process の NAPI**。デーモンは CLI / CI / pre-commit / エディタ間でキャッシュを共有するための任意の加速器と位置づける。
- 候補を並べ、計測で決める（§6-M3）。候補は (a) NAPI 同期、(b) NAPI 非同期＋内部スレッドプール、(c) UDS のデーモン、(d) 共有メモリのデーモン、(e) 起動時にプロジェクト全体を先読みコンパイルする方式。
- 旧実装の `svelte/compiler` 互換 API は外さない（他ツールが import する）。

**追記（改訂 2）: Tailwind / PostCSS を「理解」する必要はある。** 再実装しないのは**変換の実行**であって、**知識**は持つ。lint と fmt には、少なくとも次の知識が要る。

| 知識 | 例 | 使う機能 |
|---|---|---|
| 構文の方言 | Tailwind v4 の at-rule（`@theme` `@utility` `@variant` `@custom-variant` `@apply` `@source` `@plugin` `@reference`）と関数（`--theme()` `--spacing()` `--alpha()`）、PostCSS の構文プラグイン（scss/less 構文、nesting） | CSS パーサが誤検知しないこと、fmt |
| デザインシステム | 有効なクラス候補、variant、クラスの並び順、衝突するクラス | クラス並べ替え（prettier-plugin-tailwindcss 相当）、クラスの lint、`@apply` の検証 |
| 設定 | `postcss.config.*`、Tailwind の CSS エントリと `@plugin` | 上の 2 つの入力 |

反論: デザインシステムは、ユーザーの CSS エントリと **JS のプラグイン**（`@plugin`）から計算される。したがってネイティブだけでは完全には再現できない。Tailwind のコアを Rust で再実装すると、動きの速い上流を追い続けることになる。

確定:
- 構文の方言は、CSS 言語プラグインの**方言拡張**としてネイティブに持つ（パースは常にネイティブで行う）。
- デザインシステムや設定のように「JS を評価しないと決まらない知識」は、新しいプラグイン種別の**知識プロバイダ**として扱う。プロバイダは型付きの問い合わせ（このクラスは有効か、並び順のキーは何か）に答える。
  - 答えの計算には JS を使ってよい（Tailwind 自身の design system API を、プロジェクトごとに 1 回だけ評価する）。
  - 結果はコンパクトなスナップショットにして、派生物 DB（C5）に保存する。キーは入力ファイルのハッシュとパッケージの版。
  - 問い合わせ自体はネイティブで答える。
- 既定は上の「JS で 1 回評価してキャッシュ」。ネイティブ実装はプロファイルで必要と分かった部分（並び順のキーなど）に限る（§6-M7）。

### C8 oxlint / oxfmt との競合、ABI 動的プラグイン — 判定: 修正（差別化は多言語の理解。動的 ABI は 3 層の最後）

**反論**

1. **JS/TS の lint ルールで oxlint と正面衝突するのは負け戦である。** oxlint は数百のルールを持ち、フルタイムのチームがいる。差別化は「テンプレート・埋め込み・多言語を理解すること」であって、JS ルールの本数ではない。しかも oxlint はすでに `.vue` / `.svelte` / `.astro` の `<script>` を抜き出して lint している。弱点は「テンプレートを理解しない」ことであり、「DSL を全く扱えない」わけではない。
2. **Rust に安定 ABI は無い。** Rust の dylib は同じコンパイラ版でしか結合できない。ABI 越しに渡せるのは `repr(C)` とポインタだけで、アリーナの寿命を持つ Rust の木の型はそのままでは渡せない。
3. **言語プラグインの表面積は巨大である。** パーサだけでなく、埋め込み領域、semantic、lint の visitor、印字、lowering、source map のすべてに口が要る。ABI を一度公開したら、その版管理を背負い続けることになる。
4. **配布の問題。** ネイティブプラグインはプラグイン数 × プラットフォーム数（5〜8）だけ配布物が増える。加えて任意ネイティブコードの実行、macOS の公証が付いてくる。

**確定**

- JS/TS の木は自前で持つ（C10）。oxc は差し替え可能なパーサの 1 つとして使う。JS 部分の lint ルールは、自前の木の上で書き直す必要がある。ルールの本数で oxlint と競わないという方針は維持し、優先順位は次のとおりにする。
  1. テンプレートを跨ぐルールと Svelte 固有のルール
  2. 埋め込み・多言語で意味が変わるルール
  3. 一般的な JS ルール（利用頻度の高い順に、必要になった分だけ）
- プラグインは 3 層にする。

| 層 | 形 | 用途 |
|---|---|---|
| S（静的） | 同じ Cargo ワークスペースで feature を使ってリンクする。LTO とインライン化が効く | 一級の言語・ルールはすべてここ |
| N（ネイティブ動的） | C ABI ＋ 版付き vtable。木は**読み取り専用のフラットなバッファ**（固定レイアウト＋オフセット）として渡す | 第三者の言語・ルール。Tier 3 の言語で先に自分たちが使う |
| W（WASM） | コンポーネントモデル | サンドボックスが要る配布向け。任意 |

- JS 製のルール（ESLint 互換）は、N 層と同じフラットバッファを JS から読む形にする（oxc の raw transfer と同じ発想）。
- 各層の「1 ノード訪問あたりのコスト」と「木の受け渡しコスト」を計測してから、公開 API を凍結する（§6-M4）。

### C10 JS/TS の AST を自前で持ち、パーサを差し替え可能にする（改訂 2）— 判定: 維持（ただし「差し替え」の契約を固定する）

**反論**

1. **差し替え可能なパーサには変換コストがかかる。** 外部パーサ（oxc、swc など）は自分の木を作る。自前の木に移すには、木をもう一度走査してアロケーションすることになる。パースの割合が小さくなければ、この二重構築がそのまま効く。
2. **パーサごとに意味が違う。** エラー回復の有無、TS 構文の網羅度、JSX/TSX、stage 3 提案（decorators など）、コメントの保持、位置の単位（UTF-8 バイトと UTF-16 コードユニット）がパーサによって異なる。「差し替え可能」と言うには、どの差を吸収し、どの差を能力の違いとして公開するかを決めなければならない。
3. **fmt は lossless な情報を要求する。** 外部パーサがトリビアや元のトークン境界を捨てるなら、そのパーサは fmt には使えない。
4. **JS パーサを自前で書くのは大仕事で、それ自体が負債の温床になる。**

**確定**

- **自前の木（TS を含む）が唯一の正規表現**である。パーサは次の 2 通りのどちらかで木を供給する。
  - **ビルダー契約**: パーサがビルダーの trait を呼んで、自前の木を直接組み立てる。自前のパーサはこの方式で、単相化されるので間接コストはゼロ。
  - **変換アダプタ**: 外部パーサの木を自前の木に変換する。oxc はこの方式。
- 各パーサは**能力フラグ**を宣言する（lossless か、エラー回復するか、TS / JSX に対応するか、どの提案構文に対応するか）。スケジューラは、タスクが要求する能力を満たすパーサだけを選ぶ（fmt は lossless を要求する、など）。
- 位置は UTF-8 バイトオフセットに統一する。変換アダプタが換算を担う。
- **パーサ適合性**を fixture のタスク（`js.parse`）にする。corpus の script ブロックと、compile の期待出力（≒ 2 万ファイル超の実 JS）を入力にして、正規化 AST（[fixtures.md](fixtures.md) の canonical AST）が acorn / typescript-estree と一致するかを検査する。差し替えるパーサは、すべてこのゲートを通す。
- 自前パーサとアダプタ経由の oxc のパース時間を、同じ入力で比較する（§6-M6）。自前パーサが遅い間は、oxc アダプタを既定にしてよい。

### C9 型検査: TSX を捨て、推論コスト最小の TS を content mapper で渡す — 判定: 維持（互換の定義を差し替える）

**反論**

1. **drop-in の対象が変わる。** content mapper を使えば、射影テキストはユーザーの目に触れなくなる。したがって svelte2tsx のテキスト互換は目標から外せる。一方で、svelte-check が出す**診断メッセージ**には射影由来の型名が現れる（ヘルパー型の名前など）。射影を変えれば、メッセージ文字列は必ず変わる。
2. **推論コストを下げる手段には限りがある。** 注釈の無い `$props()` 分割代入のように、型が推論でしか決まらない箇所は残る。
3. **content mapper は 1 ファイルを受け取り、1 ファイル分の TS を返す。** 子コンポーネントの props 型のようなファイル間の情報は、TS の import と型参照の形で表現し、tsgo 自身に解決させる必要がある。
4. **TS 7.1 の content mapper はまだ新しいプロトコルである**（旧実装の `rsvelte_content_mapper` は protocol version 1 を実装済み）。仕様が動く前提で、版交渉を持つ必要がある。

**確定**

- 互換の定義は「svelte-check と**同じ位置に、同じ種類の、ユーザー起因のエラーが出ること**」にする。メッセージ文字列の一致は目標にしない。ヘルパー型の名前がメッセージに漏れたら、それは欠陥として扱う。
- 射影の設計原則:
  1. 注釈がある所では、注釈をそのまま型として使う（`let {a}: Props = $props()` からは推論を生まない）。
  2. コンポーネントの**公開シグネチャ**（props、events、slots/snippets、exports）を本体とは別の宣言として先頭に出す。isolatedDeclarations と同じ発想で、依存側は本体を推論せずに済む。
  3. テンプレートは JSX にせず、直線的な TS 文にする（`{#if}` → `if`、`{#each}` → `for...of`）。これで JSX の名前空間解決と、要素ごとの属性型のオーバーロード解決を避ける。要素の属性型検査は、属性がある所だけ、要素名で直接引いた型に当てる。
  4. ジェネリックなヘルパー型の連鎖（`ReturnType<typeof render>` のような「本体を推論させる」形）は禁止する。
  5. 射影の scaffolding は ignore 領域で包み、その領域の診断は mapper が落とす。
- **計測**: tsgo の `--extendedDiagnostics`（型の数、instantiation の数、check time）を、同じ project fixture 上で svelte2tsx 射影と新射影の両方について取る。これを C9 のゲートにする。
- content mapper のプロセスは、tsgo に起動される常駐プロセスである。C7 のデーモンと同じ派生物データベースを共有できる形にしておく（LSP・CLI・mapper で射影の計算を 1 回にする）。

## 4. 確定したコンセプト

**一文で**: *多言語の文書を一度だけ読み、不変の木と派生事実のデータベースから、compile・lint・fmt・型検査の射影を必要な分だけ計算する、ファイル単位並列のネイティブ・ツールチェーン。Svelte（Runes）を最初の完全な縦串とし、JS/TS を含むすべての木を自前で持ち、パーサは差し替え可能な部品にする。*

### 原則（C1 で列挙した負債クラスへの答え）

| # | 原則 | 起こりえなくなる負債 |
|---|---|---|
| P1 | 文境界・構造は**木への問い合わせ**で決める。生のソースバイトを走査して構造を決めることは禁止（lexer/parser の中だけが例外） | 文字走査による unparseable output |
| P2 | 1 つの意味論には 1 つの実装しか置かない。client/server/dev の違いは lowering の**パラメータ**であって、別の関数ではない | port が 2 つあり、しかも比べられないこと |
| P3 | 共有する木は不変にし、変換は新しい木を作る。テキストを再パースして変換を続けることは禁止 | text pipeline、再パース |
| P4 | 位置情報は `Span { lo, hi }` の 1 種類だけにし（どの文書かは文脈で決まるので持たない）、合成された位置は明示的な別の型（`SourceLocation`）にする。1 つの整数に 2 つの意味を持たせない | `loc_base` 型の二重の意味 |
| P5 | 内部表現に `serde_json::Value` を使わない。公開 JSON は印字時に書く | JSON 実体化のアロケーション |
| P6 | 意味情報は側表に置き、自前の木は `Sync` に保つ | 共有と並列の衝突 |
| P7 | 性能・正しさの主張は計測層（L0〜L2）と fixture でしか行わない | 未計測の推定に基づく決定 |

### 骨格

```
             ┌──────────────────── Kernel ───────────────────────┐
             │ SourceDb · Span/SourceMap合成 · Diagnostics ·      │
             │ Interner · Arena · QueryDB · Scheduler · Metrics   │
             └────────────────────────────────────────────────────┘
 Document ─► Surface (lossless, 言語別の木 + 埋め込み領域)
               │           └─► fmt
               ▼
           Semantic (scope / binding / 型の側表, 不変)
               │           └─► lint（Surface + Semantic）
               ▼
           Lowered IR（lowering グラフの辺ごと: Svelte→client JS / server JS /
               │          TS 射影, Sass→CSS, MD→Svelte, …）
               ▼
           Emit（テキスト + 合成した source map）
               ├─► compile 出力（Vite / CLI / NAPI）
               └─► TS 射影（content mapper → tsgo）
```

タスクは必要な派生物を `ctx.get` で求め、各派生物は文書ごとに初回だけ計算される。ファイル内では順に、ファイル間では並列に実行する。

### 非目標

- バンドル、minify、tree-shaking（Rolldown / oxc の仕事）
- Svelte 4 の legacy モードの**新規実装**。legacy ファイルは上流コンパイラへのフォールバックで扱う（node_modules 内の legacy ライブラリを Vite が compile するため、フォールバック自体は製品に必須）
- migrate（Svelte 4 → 5）
- svelte2tsx の出力テキスト互換（C9）
- JS ルールの本数で oxlint と競うこと

## 5. 最初のマイルストーン（縦串）

M0 から M4 の順に進め、各段の完了条件は計測値で書く。

1. **M0 基盤**: カーネル（SourceDb、Span、Diagnostics、Arena、Metrics L0/L1）、fixture の取り込みスクリプトとマニフェスト（§8-Q1 の決定後）、3 本立てのベンチハーネス。
2. **M1 Svelte の surface/semantic**: Runes の Svelte を parse し、公開 `parse()` の AST を上流と一致させる。fixture 全件を通す。
3. **M2 compile**: client/server の lowering を 1 つの実装で作る（P2）。上流と §8-Q2 の基準で一致させる。
4. **M3 同時実行**: fmt と lint（Svelte 固有ルールを数本）を同じ DB の上に載せ、仮説 H5 を検証する。
5. **M4 型検査**: 新射影と content mapper。C9 の計測ゲートを通す。

Tier 2 の言語（§3-C4）は、M4 の後に「埋め込みと lowering の API が 2 例目で割れないか」の検証として着手する。
