# `derived-shadowed-by-catch-and-loop-heads.svelte`

**Issue:** shadow probe

The **server** copy of the same question, and it is a separate implementation: `server/ast/read_wrap.rs` decides whether an identifier read is a derived/store binding from a `shadowed` stack whose own doc comment says it is populated "from function / arrow parameter patterns (the only shadowing the store-cluster fixtures exercise)". A `catch` clause, a `for…of` / `for…in` head and a `for (let …;;)` head all bind names and none of them was collected, so `catch (v) { v.n = 2 }` emitted `v().n = 2`, `for (let v = 0; v < 2; v++)` emitted `for (let v = 0; v() < 2; $.update_derived(v))` — a runtime call on a loop counter — and `catch ($y)` emitted `$.store_get($$store_subs ??= {}, '$y', y)`. The four hunks are independently necessary: ablating them one at a time yields 6 / 2 / 2 / 4 divergent lines. A loop head's **right-hand side** is visited before the frame is pushed, because `for (const row of list)` must still wrap the derived `list`; `unshadowed()` reads `v`, `list` and `$y` from inside every one of the four constructs as the positive control. The client was correct on all five shapes, which is why no client target moves.
